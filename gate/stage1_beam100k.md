Setting. The cleaned harness (`harness/lme_pf29.py` and its closure, after the anonymization and path edits of
`gate/wp1_wp2_edits.md`) replays the published leg `lz_u{U}_beam100k` (env row in `len_legs.tsv`: `PYTHONHASHSEED=0 PER_ARM=1
BM25LC=1 CEML=2048 CEBS=16 CE_SUBMAX=0 ... XQUOTAS=4,3,3 METHODS=flr_4_3_3 K1=200 HDETECT=0 MR_ALPHA=0 RENDER=seg3 RGROUP_MAX=-10
HBOND=doc HMARK=off ATOM=blank CHUNK=512 MSCALE=4096 U={U} NO_EXTRACT=1 EMB_MAXLEN=2048`) with `DRY=1 ROUTER_ONLY=1 DUMP_CTX=1`
(no reader, no API call), `BGE_DEVICE=cpu CE_DEVICE=cpu` (the published runs used Apple MPS on the experiment machine and
CUDA on Colab), `HF_HUB_OFFLINE=1`, the cross-encoder cache snapshot (`CE_CACHE`, 1,083 files) and a cost ledger directory
under the gate directory. 20 conversations, 400 questions. The encoder (bge-m3, max length 2048) and BM25 ran live on CPU;
every cross-encoder score was served from the cache (0 cache writes after the run; snapshot sha256 list unchanged).

Oracles. R1 = `bundle_out/len0928/full_lz_u{U}_beam100k.jsonl` (the seg3 render the harness writes; computed on Colab CUDA on

Table 6 reads consumed). Comparison: `gate/gate_compare.py` (per question, hash recomputed on both sides) and the replay's own
R1 bundle and R4 re-render (`gate/run_stage1_compare.sh`).

## U = 20 (2026-10-15 07:10–07:24 PDT, about 13 minutes, peak RSS 6 GiB, one process, `nice 10`)

| Replay R4 bundle vs R4 oracle, every field | 400 | 399 | the one difference is the metadata field `tok` (10103 vs 10107), the token count of the seg3 render |

The one seg3 difference, examined with the harness's own unit decomposition (`render_parent.py`): both contexts contain the
same twenty units (ids 0, 3, 10, 103–115, 193, 209, 218, 225 of the 257 units of conversation 4); the unit order is identical and only one
block boundary moved inside the run of units 103–115 (10 blocks in the replay, 11 in the oracle), a boundary the seg3 renderer
decides from the dense channel's scores. The reach channel was inactive on this question (`n_reach=0`), BM25 is exact, and
every cross-encoder score came from the cache, so the only quantity that can differ between a CPU and a CUDA run is the
float32 dense score, and on this question it moved a block boundary. The R4 render, which orders by parent and stored order and
ignores scores, is byte-identical on all 400 questions. This is the same single question and the same 11-character difference
that an earlier CPU replay on the experiment machine (2026-10-15 00:29–01:20, `pcap_export.sh`) found against the same
oracle.

Verdict for U=20: the contexts the paper read (R4) are regenerated byte for byte on CPU, 400/400. The seg3 intermediate is
399/400 with a documented, device-level cause. The bar of this gate is byte identity; it is met on the paper's contexts and
missed by one block ordering on the intermediate render, which is reported rather than waived.

## U = 40 (2026-10-15 07:25–07:40 PDT, about 14 minutes, one process, `nice 10`)

| Comparison | Questions | Byte-identical | Note |
|---|---|---|---|
| Replay vs R1 oracle (seg3 render) | 400 | **399** | row 4, qi 6 again |
| Replay re-rendered R4 vs R4 oracle (the paper's contexts) | 400 | **399** | row 4, qi 6: one unit differs (`tok` 20103 vs 20095) |

The one question, examined with the harness's unit decomposition and the published encoder re-run on CPU: the replay
selected unit 151 where the oracle selected unit 129 (39 of the 40 units identical). Both units are runs of slash-only lines
("/ / / ...", 1,024 and 1,023 characters, parents 15 and 18 of conversation 4), the cosine of each against the query under
bge-m3 (max length 2048, normalized) is **0.414321989 for both** (an exact float tie; dense ranks 50 and 55 of 257 on CPU),
both sit in the cross-encoder top-100 (ranks 24 and 29, scores served from the cache), BM25 ranks neither in its top-30, and
the reach channel is inactive (`n_reach=0`). The dense candidate list is an `argsort` of float32 dot products
(`core2.py:294-295`), which has no tie rule, so two units with identical scores can change places between a CUDA and a
CPU run; at U=20 the tie changed only the seg3 block order, at U=40 it changed which of the two duplicate units filled the
last slot.

Verdict for U=40: 399/400 byte-identical on the paper's contexts; the one difference is an exact tie between two
near-duplicate units resolved differently by the device, with no change in the retrieved content. The bar (400/400) is not
met and is not waived; the cause is identified to the unit and the score.
